# 真人共修 · 全局架构

> 本文记录当前实现及其测试口径。房间生命周期、超时、共同结算属于项目操作规则，不作为《選佛譜》原文引用。

## 一、产品定义

真人共修不是“同房各玩各的”，而是一局有共同开始、明确轮次和共同结束的 2–4 人对局：

1. 进入共修大厅，选择固定共修室。
2. 真人入座并分别准备；至少两位在线同修准备后，由房主开局。
3. 服务器创建 `matchId`，按入座次序轮流行动；下一局轮换首位。
4. 当前操作者完成基础一掷、全部贈掷及自动连锁后才交下一位。
5. 首位及第后进入“补齐本轮”，其余有效玩家完成本轮后共同结算。
6. 结算后分别点“准备下一局”，服务器统一清局；联机中没有个人重开。

AI 对手已删除。“问义”是独立的经据解释功能，不属于 AI 同修。

## 二、房间状态机

```text
waiting
  ├─ ready_set（各自准备/取消）
  └─ start_match（房主且至少两人准备）
       ↓
playing / waiting_toss
  ├─ 非当前玩家 toss_request → 拒绝
  ├─ 当前玩家 toss_request → 服务器生成轮相并提交棋况
  └─ playing / resolving
       ├─ turn_done + bonus > 0 → 同一玩家 waiting_toss
       ├─ turn_done + bonus = 0 → 下一位 waiting_toss
       └─ 有人及第 → finishing=true，补齐当前轮
            ↓
finished
  ├─ ready_set（准备下一局）
  └─ start_match → 全体权威清局，进入新 matchId
```

每次状态变化增加 `revision`。掷轮命令必须携带 `requestId`；相同编号重复发送只返回原结果，不重复增加掷数。

## 三、操作规则边界

- `贈 N 擲`：当前操作者即时获得 N 次续掷。
- 纯贈：保持当前位置后续掷。
- 移位兼贈：先移动，再从目的位续掷。
- 嵌套贈掷：继续追加到同一操作者队列。
- 赠掷未结束前不交轮。
- 以上是本项目定稿操作规则；谱位事实、谱曰原文、释义和操作规则在证据层保持分开。

## 四、权威边界

| 层 | 文件 | 职责 |
|---|---|---|
| 纯规则引擎 | `src/sfp-engine.js` | 起行、安住、移位、贈掷、自动连锁、终点；浏览器与 Worker 共用 |
| 共修室 Durable Object | `worker/index.js` | 轮相随机、请求幂等、房间状态机、轮次、掉线、共同结算、聊天 |
| 联机客户端 | `src/net.js` | WebSocket、重连、准备/轮次/结算 UI、聊天与密码邀请 |
| 3D 游戏适配 | `src/game.js` | 按服务器承诺的组合播放木轮、判词和棋珠动画 |
| 广场 Durable Object | `worker/index.js` 固定对象 | 各室快照、掷轮总数、及第录、公报和锁数上限 |

服务器不接受客户端上报 `pos/n/done`。旧 `move` 与 `restart_self` 命令会返回 `old_protocol`。

## 五、中断与离席

| 事件 | 当前行为 |
|---|---|
| 在线 60 秒未掷 | 本手空过；连续两次后标记“暂离”，后续跳过 |
| 当前玩家断线 | 将本手等待缩短为 30 秒；座位仍保留 |
| 意外断线 | 90 秒内凭原 `playerId` 重连，棋况以服务器快照恢复 |
| 主动离席 | 立即移出行动顺序；若正在行动则交下一位 |
| 有效玩家少于两位 | 本局以 `not_enough_players` 中止并共同结算 |
| 房主离席 | 最早仍在室的成员自动递补为房主，珠色不变 |
| 对局中后来者 | 可聊天与旁观，标记“候下局”，不插入本局行动顺序 |

房间最后一个 WebSocket 断开时不再立刻删除状态；由 Durable Object alarm 在保座期后清理。

## 六、聊天交互

- 展开聊天后，点击面板外任意处立即缩小；遮罩会拦截第一下点击，避免穿透到掷轮、相机或星位。
- 点聊天标题空白处、按 `Esc`、向下拖抓手也可缩小。
- 输入框、发送、快语、房间按钮和消息滚动区保持可操作。
- 手机键盘出现时使用 `visualViewport` 抬升面板；缩小时输入框失焦。
- 面板包含 `role=dialog`、`aria-expanded`、状态 `aria-live` 与不少于 44px 的关键按钮。
- 聊天每连接最短间隔 750ms，单条最多 200 字；历史只在初次入座/重连的全量同步中发送。

## 七、编址与访问

| 概念 | 形式 |
|---|---|
| 厅 | `H{n}`；每厅 12 室 |
| 室 | `H{厅}T{室}`，如 `H1T12` |
| 座 | 0–3 仅供服务器维持入座与轮流次序；前台不显示方位，首位为房主 |
| 珠色 | 金、青、赭、藕；跟人不跟座 |
| 密码 | 四位数字，加盐哈希后保存 |
| 邀请链接 | `#r=H1T5.3333` |

## 八、验证

先启动本地 Worker：

```bash
npm run server
```

再运行：

```bash
npm run test:engine
npm run test:net
NET_BASE=http://127.0.0.1:8787 npm run test:plaza
npm run test:plaza-client
npm run check:grant
npm run build
```

重点断言包括：

- 入座不会自动开启个人谱局；
- 一个人同一时间只进入一个房间，重复点击复用同一身份与座位；
- 只有准备玩家进入本局顺序；
- 非当前操作者和客户端伪造位置会被拒绝；
- 重复 `requestId` 不会重复行棋；
- 贈掷留在当前操作者；
- 中途进入只旁观；
- 重连读取服务器棋况；
- 日常名单同步不重复下发全部聊天；
- 广场正确区分候场、行谱中和满座。
